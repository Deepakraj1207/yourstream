# Local media library (Phase 4)

Module `:library` (repositories, sync, use cases) on top of `:core:database` (Room, schema v3).

```
media index (Phase 2/3) ──triggers──► library_pending ──► LibrarySynchronizer ──► library tables
                                                           (batched, incremental)       │
                       MediaRepository · MovieRepository · SeriesRepository · EpisodeRepository
                       WatchHistoryRepository · SubtitleRepository · AudioTrackRepository
                       use cases: SearchMedia, GetMovies, GetSeries, GetEpisodes, UpdateWatchProgress,
                       MarkAsWatched, GetContinueWatching, GetRecentlyAdded, GetRecentlyWatched,
                       GetFavorites, ToggleFavorite, MergeMedia, GetItemDetails, SyncLibrary
```

## Database relationships

```
library_item (kind = MOVIE | SERIES | VIDEO, match_key UNIQUE)
 ├─< season (series_id, number UNIQUE per series; -1 = season-less numbering, 0 = specials)
 │    └─< episode (season_id, number UNIQUE per season; series_id + season_number copied for sorting)
 ├─< media_link >── media          one row per file: item (+ episode); AUTO | MANUAL | EXCLUDED
 ├─< library_item_language         ISO codes of the item's files (filterable)
 ├─< library_alias                 old match keys → item (merges are remembered)
 ├── library_item_fts              FTS4 over title + search_text
 │
 │  USER DATA (never removed by sync)
 ├─< favorite                      1:1
 ├─< watch_state                   PK (item_id, episode_key): 0 = the item itself, else episode id
 ├─< watch_history                 one row per viewing session
 └─< track_preference              audio/subtitle language, subtitles on/off, offset
subtitle_track ── item/episode (SET NULL), media (EXTERNAL file), for_media (EMBEDDED)
audio_track ──── media            PARSED (from the name) | PROBED (from the file, Phase 8)
library_pending, library_dirty_item   work queues filled by SQLite triggers
```

| Kind | Identity (`match_key`) | Holds |
|---|---|---|
| MOVIE | `movie:<title key>:<year>` (a year-less file joins the only dated movie with that title) | versions (`media_link`, no episode) |
| SERIES | `series:<title key>` | seasons → episodes → versions; season packs link to the series with no episode |
| VIDEO | `video:<media id>` | one unidentifiable file (title confidence < 0.5, or no title) |

Rules that protect user data:
- **Sync only creates, relinks and recomputes.** It deletes an item or episode only when it has no live files **and** no favorite, progress or preference, and is not locked. Otherwise the item stays, shown as *unavailable*.
- **`watch_state.episode_key` is deliberately not a foreign key**, so rebuilding an episode row cannot cascade progress away.
- **Identity is the match key, never a row id.** A file that disappears and comes back (re-scan, chat re-added) lands on the same item, with its progress intact.
- **Manual changes win:**
  - edits and merges lock the item;
  - MANUAL and EXCLUDED links are never touched by sync;
  - a hidden (deleted) item keeps its files, so it does not reappear;
  - merges add an alias, so future files of the old spelling follow the merge.

## Queries

- **Lists** (search, movies, series, recently added, favorites) are generated by `LibraryQueryBuilder`:
  - **Filters**, all optional: FTS text (`library_item_fts MATCH 'tom* and* jerry*'`), kinds, favorites, watch status (unwatched / in progress / watched, series-aware), year range, language (`EXISTS` on `library_item_language`), minimum resolution, unavailable, hidden.
  - **Sorts**: title (articles ignored), recently added, recently watched (never-watched last), year, size, each reversible.
  - **Safety**: only whitelisted SQL fragments are concatenated. User input is always a bound argument, and FTS input is reduced to letters and digits.
  - **Stability**: every `ORDER BY` ends with the primary key, so ties never reorder rows between pages.
  - **Shape**: one row = item + favorite flag (LEFT JOIN on PK) + the item's own progress (LEFT JOIN on PK `(item_id, 0)`). There are no per-row subqueries; series watch counts are cached columns.
- **Episodes**: by series (and optionally season), ordered by season then number, with each episode's progress joined.
- **Continue watching**: in-progress units, newest first, one per item (the most recently played episode of a series).
- **Recently watched / history**: `watch_state` and `watch_history` by time.
- **Versions**: an item's or episode's files, best first (live first, then resolution, then size).
- **Aggregates** (`available_count`, `latest_added_at`, `max_resolution`, `total_size`, season/episode counts, languages, search text) are recomputed per touched item during sync. `watched_count` and `last_watched_at` are kept by the watch repository on every progress change.

## Pagination

- Every potentially long list returns `Flow<PagingData<…>>` straight from a Room `PagingSource`: items, episodes, recently watched and history.
- Page sizes: 50 for items, 100 for episodes. `maxSize` is 8 pages, so pages scrolled far away are dropped and memory stays bounded.
- Dynamic lists use `@RawQuery(observedEntities = …)`, so they refresh when items, favorites or progress change.
- Tests walk the `PagingSource` page by page (25 rows per page, 260 rows, every sort) and assert every row appears exactly once.
- Continue watching is a small `Flow<List>` with a limit, which is fine for a row of about 20.

## Migration strategy

| From → to | How | Data |
|---|---|---|
| 1 → 2 | Room auto-migration | adds parsed-metadata columns with defaults; rows kept; old parses flagged for re-parse |
| 2 → 3 | Room auto-migration with `V3` spec | only **adds** tables. `onPostMigrate` installs the triggers and queues every existing file in `library_pending`, so the first sync builds the library from the index; no data is moved or dropped |

- **No destructive fallback.** `fallbackToDestructiveMigration` is never enabled, so a missing migration fails at startup instead of wiping progress.
- **Schemas are committed** (`core/database/schemas/1.json`–`3.json`). `MigrationTest` creates real v1 and v2 databases with rows, migrates to v3, validates against the exported schema, and checks the data and the triggers.
- **Triggers live outside Room's model.** They are recreated idempotently on every open (`YourStreamDatabase.CALLBACK`). Their inserts use `WHERE NOT EXISTS`, because SQLite lets the firing statement's conflict clause (Room's `UPDATE OR ABORT`) override a trigger's own `OR IGNORE`.
- **Library tables are derived and can be rebuilt; user-data tables are not.** Future schema changes to user-data tables must use hand-written, tested migrations.

## Performance

- **Incremental by construction.** Triggers queue exactly the files that changed, so a sync after a scan touches those files only. Unchanged files are skipped by comparing a signature of their parse with the one stored on the link.
- **Batched.** 500 files per transaction, with aggregates recomputed only for the items those files touched.
- **Measured** (`LibraryScaleTest`, Robolectric on the build machine, with debug output):

  ```
  10,000 files (2,000 movies, 200 series × 40 episodes)
  first sync 2.5–2.8 s · first page 11–140 ms · FTS search 12–32 ms
  one new episode: re-sync 5–14 ms, and its series jumps to the top of "recently added"
  ```

- **The triggers add no measurable cost.** The indexer's 20,000-row write test took 12 s with the triggers and 14 s without. The bulk of that time is the Phase 3 parser, at about 0.5 ms per file.
- **Index changes are coalesced.** `LibrarySyncTrigger` debounces them (750 ms) and runs one sync at a time off the main thread.
